## Verification Note (Oct 1 2026, independent audit)

* **Stub Synthesis Success Rate (3/3)** — **confirmed**. Re-compiled all three harnesses (`poll_in`, `poll_out`, `isr`) from scratch during this audit using the project's documented build flags; all three compile clean, start up with no ASan/UBSan violations, and fuzz without crashing on startup. See `RESULTS.md`/`STAGE6_HARNESS_METRICS.md` verification notes for detail.
* **Incorrect Mock Rate (2/6, 33.3%)** — **confirmed**. Both cited divergences are real and present in the current harness source: the W1C clobbering comment and conditional assert in `harnesses/fuzz_pl011_isr.cpp` (lines ~120-127), and the `poll_out`/`fr`-bit busy-wait hazard documented throughout Stage 6. The 6 named register types (`cr`, `fr`, `dr`, `mis`, `icr`, `imsc`) all appear in the harness sources as claimed.
* **Peripheral Identification Precision (53/53 post-fix) and Register Identification Recall (100%)** — **follow-up (Oct 1 2026): the "different units" theory below is ruled out; this is a real, unexplained discrepancy, not a reconciliation gap.** Re-running `stage1_ast_parser.py` fresh against `zephyr-src/drivers/serial/uart_pl011.c` (the same source these figures are about) extracts **42** total `mmio_accesses` across 29 functions, not 53. The "53" figure matches `llm_proposals.json`'s entry count exactly, so the original note here speculated the two numbers might describe different units (e.g. a raw per-function access count vs. some deduplicated-by-register-name count downstream). Checking that theory directly: `stage2_llm_synthesizer.py`'s merge loop (`for func_name, func_data in ast_data["functions"].items(): for access in func_data["mmio_accesses"]:`) does a flat 1:1 pass over Stage 1's `mmio_accesses` list with **no deduplication or filtering at all** — each entry becomes exactly one `llm_proposals.json` key (`func::reg::line`). There is also only ever one version of `stage1_ast_parser.py` in git history (`git log --all` shows a single commit), so this isn't a case of the script's extraction logic having since changed either. Put together: running the current, only-ever-committed Stage 1 script against the current source, then the current, dedup-free Stage 2 script against that output, cannot mathematically produce 53 entries from 42 upstream accesses. So "53" was not produced by this exact pipeline as it exists in the repo today — it's a genuine contradiction, not an unlabeled-units gap. Possible explanations that remain open (none checkable from what's in the repo): `llm_proposals.json` was generated against a slightly different revision of `uart_pl011.c` than the one currently committed, or against a since-modified version of the extraction script that was never separately committed, or the 53 entries include some manually-added/non-`stage1`-sourced rows. This needs the original run's provenance (which commit of the driver source, which script revision) to fully close out; flagged here rather than silently assumed correct either way. The pre-fix "169 total flagged / 116 false positives" figures could not be checked at all — they describe a heuristic bug that has since been fixed, so there is no way to regenerate the old buggy output to confirm the historical count, and no saved log of that specific run was found in the repo.
* **Runtime Fault Rate (2/4, 50%)** — **partially confirmed, denominator unclear**. The two named faults (`poll_out` busy-wait timeout, `isr` v1 assertion crash) are both real and independently verified elsewhere in this audit. The "4 independent harness-level compile+fuzz evaluation sessions" denominator (`poll_in`, `poll_out`, `isr` v1, `isr` v2) is plausible but not independently checkable from any saved log — noting this is a softer, lower-confidence figure than the numerator.

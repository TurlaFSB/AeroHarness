## Verification Note (Oct 1 2026, independent audit)

* **Stub Synthesis Success Rate (3/3)** — **confirmed**. Re-compiled all three harnesses (`poll_in`, `poll_out`, `isr`) from scratch during this audit using the project's documented build flags; all three compile clean, start up with no ASan/UBSan violations, and fuzz without crashing on startup. See `RESULTS.md`/`STAGE6_HARNESS_METRICS.md` verification notes for detail.
* **Incorrect Mock Rate (2/6, 33.3%)** — **confirmed**. Both cited divergences are real and present in the current harness source: the W1C clobbering comment and conditional assert in `harnesses/fuzz_pl011_isr.cpp` (lines ~120-127), and the `poll_out`/`fr`-bit busy-wait hazard documented throughout Stage 6. The 6 named register types (`cr`, `fr`, `dr`, `mis`, `icr`, `imsc`) all appear in the harness sources as claimed.
* **Peripheral Identification Precision (53/53) and Register Identification Recall (100%)** — **fully resolved (Oct 3 2026): the "53 vs. 42" reproducibility gap is closed, not just explained.** Root cause, confirmed mechanistically rather than by provenance-guessing: all 11 missing accesses (42 → 53) were the identical pattern, `get_uart(dev)->reg` — a helper-FUNCTION call whose return type is the MMIO struct pointer, as opposed to a bare struct-typed local variable (`volatile struct pl011_regs *uart = ...`). Confirmed directly against the real source: all 10 affected functions (`pl011_disable`, `pl011_enable`, `pl011_err_check`, etc.) call `get_uart(dev)->reg` inline with no local re-declaration of the pointer's type anywhere in `uart_pl011.c` itself. `stage1_ast_parser.py`'s MMIO-base heuristic could only ever recognize `get_uart` as an MMIO accessor by seeing its real declaration (`volatile struct pl011_regs *get_uart(const struct device *dev)`, in the separately-`#include`d `uart_pl011_registers.h`) — and `tu.cursor.get_tokens()` on the *main* file's parse never includes tokens from an included header at all, confirmed by direct introspection (this is `get_tokens()`'s normal scope, not a parse failure; a full `-I zephyr-src/include` instead cascades into dozens of unrelated missing `CONFIG_*`/arch defines, not worth it just for this). Fixed by having `stage1_ast_parser.py` additionally parse each of the source file's own local, quote-style `#include "X.h"` headers as their own standalone translation units purely to extend the mmio_bases set — confirmed this lets `uart_pl011_registers.h` contribute `get_uart` even though its own one remaining dependency (`zephyr/device.h`) still doesn't resolve (a fatal diagnostic doesn't stop clang's lexer from tokenizing the rest of that file's own text, only from pulling in further headers). **Verification performed:** a fresh run against the current, unmodified `uart_pl011.c` now produces exactly 53 entries, and a full `(function, register, line)` triple-level diff against the committed `llm_proposals.json` is an exact match — not just the same total. Also re-ran against the Kinetis ADC driver (`adc.c`, the other real target this script is used on) before and after the fix: identical output (18 accesses for `kinetis_adc_calibrate`, 35 total) — no regression. The pre-fix "169 total flagged / 116 false positives" figures remain unverifiable for the same reason as before (describe a since-fixed heuristic bug, no saved log of that specific historical run exists).
* **Runtime Fault Rate (2/4, 50%)** — **partially confirmed, denominator unclear**. The two named faults (`poll_out` busy-wait timeout, `isr` v1 assertion crash) are both real and independently verified elsewhere in this audit. The "4 independent harness-level compile+fuzz evaluation sessions" denominator (`poll_in`, `poll_out`, `isr` v1, `isr` v2) is plausible but not independently checkable from any saved log — noting this is a softer, lower-confidence figure than the numerator.

## Stage 6: Ground-Truth Methodology Validation (CVE-2020-10062)
* **Result (METHODOLOGY VALIDATION / POSITIVE CONTROL)**: Evaluated the pipeline against a known ground-truth vulnerability (CVE-2020-10062: MQTT `packet_length_decode` off-by-one integer overflow) to validate capability. **Note: This is a positive control, NOT a new vulnerability discovery.**
* **Findings**:
  * **Isolated Harness**: Found 0 crashes. The unsigned integer overflow inside `packet_length_decode` is well-defined behavior in C and physically causes no memory-safety violation in isolation.
  * **Broad-Scope Safe Harness (`mqtt_handle_rx`)**: Found 0 crashes. The Zephyr library code remains memory-safe internally (network reads are bounds-checked). The bug is strictly an API contract violation where a corrupted length is passed up to the application.
  * **Broad-Scope Vulnerable Consumer Harness**: **Detected the vulnerability within hundreds to low thousands of executions (<1 second), real crash counts 610/809/1445 across 3 independently-seeded fresh runs.** Modeling a naive application consumer (a dummy callback trusting `payload.len` for a `memcpy`) allowed the fuzzer to organically trigger the API contract violation and crash via an AddressSanitizer stack-buffer-overflow.
  * **Reproducibility gap found and fixed (Oct 1 independent re-audit)**: the committed `fuzz_broad_vuln` binary does genuinely detect the crash (re-confirmed) — the original "<1 second" claim is real on that pinned binary. However, **rebuilding `harness_broad_vuln.c` from source using this project's own documented build flag (`-O1`, per `REPRODUCE.md`) silently fails to reproduce the crash at all** — confirmed via a real 9.8M-execution fuzzing campaign on a fresh `-O1` rebuild, 0 crashes. Root cause, confirmed via direct LLVM IR inspection: at `-O1`, with `app_buffer`'s contents never read after the `memcpy`, LLVM's optimizer dead-code-eliminates the entire `malloc`/`memcpy`/`free` sequence in `dummy_cb`, so the vulnerable code silently never executes at that optimization level. Fixed by adding a single `volatile` read of `app_buffer[0]` immediately after the `memcpy` in `harness_broad_vuln.c`, forcing the copy to be observable and preventing the optimizer from removing it. The committed binary has been rebuilt from this fixed source at the documented `-O1` flag and re-verified: detects the crash both from the saved `trigger.bin` and from a real fuzzing campaign (fresh mutated input, crash within hundreds to low thousands of executions across 3 independently-seeded runs: 610/809/1445). The two unaffected negative controls (isolated harness, broad-safe harness) were re-confirmed clean (0 crashes, ~10M and ~5M executions respectively) after the same rebuild.
* **Mechanistic Discovery**: In the broad-scope harness, the fuzzer organically found **two distinct paths** leading to the exact same massive `payload_len` API violation:
  1. **Official CVE Path (Overflow)**: A 5-byte length where the 5th byte lacks a continuation bit causes `packet_length_decode` to overflow into a massive positive `var_length`, cascading into `publish_decode` (verified manually).
  2. **Fuzzer-Discovered Path (Underflow)**: A 6-byte input triggering `var_length = 0` alongside a QoS/Topic header requiring 4 bytes causes `publish_decode` to blindly calculate `0 - 4`, underflowing into a massive `payload_len`.

## Stage 7 Extension: RL-Guided State-Machine Sequencing (Methodology Case Study)
* **Result (Honest Null Finding)**: On this mock PL011 driver, Blind Random, Constrained Random, UCB1, and all three Q-learning tie-break variants converge to **identically flat driver-level coverage (29 PCs)**. No sequencing policy outperformed blind random on this benchmark.
* **Why (The 90% Ceiling)**: A single random 10-step episode covers ~90% of the driver's reachable branches (26 out of 29 PCs at Execution 1). The benchmark state space is far too shallow for any intelligent sequencing to differentiate itself in principle, regardless of the reinforcement learning policy quality.
* **Limitation**: The null result is a reflection of this benchmark's bounded depth (a mock driver with shallow initialization requirements), not a general claim against RL-guided fuzzing. 
* **Future Work**: Evaluating RL against random fuzzing requires a deep mock driver with long, stateful prerequisite chains, explicitly scoped as follow-on work.

### The Real Contribution: The Measurement Failure Chain
The primary contribution of this stage is methodological. Over several iterations, the RL agent appeared to repeatedly "outperform" the random baselines. Each apparent victory was systematically unmasked as a measurement artifact or reward-hacking vulnerability inside the fuzzer's custom `__sancov_cntrs` C-loop. 

This 8-point failure chain serves as a crucial methodology lesson for anyone building custom reward signals on raw LibFuzzer coverage counters:

1. **8-bit Counter Wraparound → Unsigned Underflow**: LibFuzzer's 8-bit counters wrap to zero when hit 256 times. A naive `delta = new_cnt - old_cnt` computation underflowed, granting the RL agent a spurious ~10^19 reward.
2. **Clamped Delta → Insufficient Fix**: Clamping the underflow to zero merely changed the exploit's shape. The agent discovered it could milk continuous `0 → 1` transition loops at the wraparound boundary.
3. **Sticky Monotonic Bitmap**: A permanent `sticky_cov[index] = 1` map was required to close the exploit for real, enforcing a strictly non-stationary, depletable reward landscape.
4. **Baseline-Drift Scoping**: The raw `__sancov_cntrs` read was silently undercounting coverage across all algorithms due to wrap noise. A dedicated audit isolated this vulnerability strictly to Stage 7's custom scoring path; Stages 1–6 were confirmed immune as they parsed LibFuzzer's monotonic `cov:` stdout instead.
5. **Debug Printf Self-Reward ("Heisenberg Bug")**: An errant `printf("MAX_COV...")` statement injected a 2-edge branch into the fuzzer loop. The fuzzer rewarded itself for executing its own diagnostic trace statement, artificially inflating scores.
6. **Tie-Break Death-Loop**: Once the sticky-bitmap rewards depleted, all Q-values mathematically decayed to zero. A degenerate deterministic tie-breaker (`cmd=0`) caused Q-learning to collapse into an initialization death-loop, artificially plunging coverage below random (26 PCs).
7. **Randomized Tie-Break (False Recovery)**: Randomized tie-breaking appeared to recover coverage to a staggering 54 PCs. However, this "win" was proven false: the RL agent was simply being rewarded for executing the increasingly complex internal decision trees of its own `switch/case` router and epsilon decay branches. 
8. **Final Structural Fix (no_sanitize("coverage") + llvm-cov)**: Applying `__attribute__((no_sanitize("coverage")))` to all fuzzer/agent code and compiling with `-fno-inline` strictly scoped measurement to the target driver. This collapsed the entire RL superiority narrative, revealing a flat 29 PCs across all algorithms. This flatline was completely, independently verified via `llvm-cov` source-based profiling.

## Stage 6 Ablation: Informed vs. Blind Harness Construction (Oct 1 2026)
* **Question**: Does Stage 2/3's semantic MMIO modeling (per-field Constant/Passthrough/Bitextract/Set behavior, isolating the specific bits that gate branches into dedicated fuzzer bytes) actually buy more coverage than an engineer with no hardware-semantic analysis would get by just raw-fuzzing the whole register struct? This had never been tested — it is implicitly assumed throughout Stages 6/7 but never isolated as its own variable.
* **Method**: For each of the 3 isolated Stage 6 harnesses, built a byte-for-byte identical "blind" variant (`harnesses/fuzz_pl011_{poll_in,poll_out,isr}_blind.cpp`) that differs in exactly one respect: instead of the informed harness's per-field model (e.g. `regs.fr = data[2] & PL011_FR_RXFE`), it does `memcpy(&regs, data, sizeof(regs))` — a raw, unstructured 76-byte copy of fuzzer bytes onto the whole `pl011_regs` struct, with no field-level reasoning at all. All software-state mocking and correctness assertions are unchanged, so register-value construction is the only variable. Ran the same multi-seed protocol used for the informed baseline (5 seeds, `-max_total_time=15s` each for `poll_in`/`isr`; 10 seeds, run-until-hang for `poll_out`, matched by re-running the informed `poll_out` baseline at 10 seeds too for a fair comparison — the original C1 audit only used 5). Cross-validated with `llvm-cov` using the same methodology as Stage 6/C3 (raw logs in `blind_llvm_cov_logs/`, fuzzing logs in `blind_fuzz_logs/`, binaries pinned as `fuzz_poll_in_blind`/`fuzz_poll_out_blind`/`fuzz_isr_blind`).
* **Result — `poll_in` and `isr` (shallow functions, few branches): no measurable difference.**
  * `poll_in_blind`: **identical** `cov:11/ft:12` (full coverage of 17 PCs) across all 5 seeds — exactly matching the informed harness.
  * `isr_blind`: **identical** `cov:16/ft:17` (of 24 PCs) across all 5 seeds — exactly matching the informed harness.
  * Both plateaus were reached in well under 20,000 executions (a few hundred milliseconds), despite the blind harness's fuzzer-controlled input being ~76 bytes of raw, undifferentiated register bytes vs. the informed harness's 1-3 dedicated, pre-isolated bytes. For functions this shallow, libFuzzer's own coverage-guided mutation rediscovers the relevant bit patterns from scratch essentially for free — the semantic head start made no measurable difference to the coverage ceiling or the time to reach it.
  * `llvm-cov` cross-validation on the blind harnesses' own `.cpp` files shows 96.55%/95.35%/91.67% (poll_in) and 96.88%/92.45%/88.89% (isr) region/line/branch coverage — slightly below the informed harnesses' reported 100%. Traced this gap to its source with `llvm-cov show`: in both cases the only persistently-uncovered lines are the harness's own trivial minimum-input-size guard clause (`if (size < ...) return 0;`), which libFuzzer's corpus minimization discards once redundant at the sancov-edge level — **not** a gap in actual target-function (`pl011_poll_in`/`pl011_is_readable`/`pl011_isr`) execution, which shows full coverage in both. This is a benign corpus-minimization/measurement artifact, not a real capability difference, and is reported here rather than silently rounded away.
* **Result — `poll_out` (has a real hazard: a single bit gates an infinite busy-wait): informed harness meaningfully more likely to reach deeper coverage before hanging.**
  * Across 10 seeds each (run-until-timeout protocol, `-timeout=3`): the **informed** harness hung at the deeper `cov:5/ft:6` state in **9/10 seeds**, and at the shallow `cov:2/ft:2` state in only 1/10. The **blind** harness hung at `cov:5/ft:6` in only **3/10 seeds**, and at the shallow `cov:2/ft:2` state in 7/10 — roughly the inverse frequency.
  * Interpretation: `PL011_FR_TXFF` is a single bit that, once set, causes an immediate infinite loop (and libFuzzer timeout/process death) with no further exploration possible from that input. The informed harness isolates this one bit into a dedicated byte (`data[0] & PL011_FR_TXFF`), so a mutator has to flip roughly 1 relevant bit out of 8 to trigger it. The blind harness buries the same bit inside a 76-byte raw struct alongside everything else influencing the rest of the function's behavior — so the mutator is statistically far more likely to stumble into the hazard bit while still exploring shallow states, before it has had a chance to reach the deeper `cov:5` region. This is the first part of the project where semantic register modeling shows a real, quantifiable, needle-in-a-haystack-search benefit, as opposed to a blanket coverage multiplier.
  * `llvm-cov` cross-validation (single safe pre-hang corpus replay, matching the C3 methodology) gives `poll_out_blind` 82.61% lines / 50.00% branches — essentially identical to the informed harness's previously-reported 83.33% lines / 50.00% branches, confirming the sancov-level finding is not a cross-validation artifact in either direction.
* **Takeaway**: Stage 2/3's semantic MMIO modeling does not act as a blanket coverage multiplier — for functions with few, shallow, easily-discoverable branches, blind raw-byte fuzzing converges to the identical coverage ceiling with no measurable cost in time or executions. Its real, measurable value is concentrated on hazards that are a small fraction of a much larger raw search space (here, 1 bit out of 76 bytes): isolating the relevant bits into dedicated fuzzer-controlled bytes substantially increases the odds of reaching deeper coverage before an unguided mutator accidentally triggers the hazard and ends the run. This is a more precise, evidence-grounded claim than "informed harnesses find more coverage," and should replace any such blanket claim in the paper.
* **Scripts**: `harnesses/fuzz_pl011_{poll_in,poll_out,isr}_blind.cpp` (harness sources); fuzzing logs in `blind_fuzz_logs/`; `llvm-cov` reports in `blind_llvm_cov_logs/`; representative corpora in `blind_corpus/`.

Real output (`stage3_oracle_kinetis_adc.log`): **5 Confirmed, 13 Unconfident, 0 Disagreements.** The 13 Unconfident entries are the 12 passthrough arithmetic-sum registers (`CLP0`-`CLPS`, `CLM0`-`CLMS`) plus `SC3`'s initial trigger write at line 118 — none of these sit inside a `WHILE`/`IF`/`SWITCH` statement, which is exactly the AST pattern class this oracle is built to recognize and exactly the class it is designed to decline to judge rather than guess at.
* **A new, more severe static-mocking limitation class, found and fixed**: the target function sets its own calibration-trigger bit and then immediately spins on that same bit (`dev->SC3 |= ADC_SC3_CAL_MASK; while (dev->SC3 & ADC_SC3_CAL_MASK) {}`) — unlike Zephyr's previously-documented busy-waits (gated by a *fuzzer-controlled* bit, so some inputs avoid the hang), no static single-shot struct mock can ever un-set a bit the function just set itself, making this function **unconditionally unfuzzable (100% hang) under the project's established mocking approach, for every input, with no exception.**
  * **Four self-repair iterations were attempted; the first three genuinely failed under real fuzzing, each diagnosed with real debug-instrumented tracing, not assumed:**
    1. Per-call `pthread_create`/`join` per `LLVMFuzzerTestOneInput` invocation — compiled clean, worked on a single replayed input, hung under real fuzzing after the first few mutations.
    2. One persistent helper thread signaled via a busy-poll flag — still hung. Debug tracing (stderr prints inside the helper loop) showed the helper fired exactly once, then was never scheduled again: the helper's idle busy-spin and the main thread's own busy-wait (inside the target function) starved each other for this sandbox's limited CPU scheduling.
    3. The textbook fix for #2 — the helper properly blocking on a condition variable instead of spinning when idle — still hung. A second debug-instrumented copy showed the *first* execution's full handshake (trigger → wake → clear → re-wait) tracing perfectly, but the *second* execution never even reached the "about to lock" print on the main side before the 3-second alarm fired, implicating `pthread_once`/thread-handoff reliability itself in this sandbox, not the spin-vs-block choice.
    4. **Working fix**: dropped threads entirely in favor of a POSIX interval timer (`timer_create`/`CLOCK_REALTIME`) delivering a dedicated `SIGUSR1` signal (chosen specifically to avoid colliding with libFuzzer's own `SIGALRM`-based watchdog) to a handler that clears the bit. A first attempt using a **one-shot** timer firing ~200µs out still hung — direct debug tracing proved the handler *did* fire, but a one-shot timer races the target function: if the signal lands before the function's own `dev->SC3 |=` write executes, the handler clears a bit that isn't set yet (a no-op), the bit then gets set, and since the timer never fires again, it is never cleared. Switching to a **periodic** timer (firing every ~50µs, re-arming automatically via `it_interval`) fixes this: clearing an already-clear bit is harmless, so an early "missed" firing costs nothing, and a later firing is guaranteed to land after the bit is genuinely set. **Confirmed directly**: a replayed input with the (separate, fuzzer-controlled) `SC1`/`COCO` bit set completes in 0ms with no hang on the self-set `SC3`/`CAL` bit, where the three prior iterations all hung on exactly this line.
* **A second, independent busy-wait remained — and is a genuine instance of the already-documented fuzzer-controlled-bit hazard class, not a new bug**: immediately after the self-hazard, the real driver has `while (!(dev->SC1[0] & ADC_SC1_COCO_MASK)) {}`, gated by a plain fuzzer-controlled bit in `data[0]`. This is the exact same busy-wait class already documented for Zephyr's `poll_out` (see the ablation above) — a single bit, once wrong, causes an immediate, unrecoverable libFuzzer timeout for that input, ending the run. On this function the effect is more pronounced than `poll_out`'s: because the COCO bit sits on `data[0]`, the very first byte past the harness's minimum-length check, roughly half of all length-qualifying mutations hang immediately with zero prior progress, rather than after exploring a deeper region first.
* **Multi-seed fuzzing campaign (10 seeds, run-until-hang protocol, `-timeout=3`, matching the established methodology)**:
  * **7 of 10 seeds hung immediately** at `cov:2/ft:2` (i.e. on the very first length-qualifying mutation, before any real exploration) — consistent with the COCO-bit hazard sitting on the first fuzzer-controlled byte.
  * **3 of 10 seeds (seeds 5, 7, 9) escaped the immediate hang and reached deeper coverage** (`cov:9`, `ft:10`–`15`) before eventually also hanging — these are the seeds whose early mutations happened to set the COCO bit.
  * This is a real, honestly-reported result, not a sign the harness is broken: it is the same "single-bit-hazard-in-a-larger-search-space" pattern the ablation study already documents for `poll_out`, just with a higher hang rate because the hazard bit here sits on the very first input byte rather than being buried deeper.
* **`llvm-cov` cross-validation** (built a second `-fprofile-instr-generate -fcoverage-mapping` binary, replayed every corpus entry saved across all 10 seeds, merged profiles — raw report in `kinetis_llvm_cov_logs/kinetis_adc_calibrate.txt`): despite the modest raw sancov numbers above, the real driver function `kinetis_adc_calibrate` itself reaches **100% line coverage (18/18), 91.67% region coverage, 83.33% branch coverage** across the corpus that did survive — including both the CALF-failure early-return path (9/12 replayed inputs) and the full PG/MG gain-calibration arithmetic path (3/12 replayed inputs). This confirms that once an input survives past the two busy-waits, the harness exercises the real target thoroughly and faithfully, consistent with the project's established finding (first documented for Zephyr's `isr`) that raw sancov edge counts and source-level `llvm-cov` coverage are different, non-interchangeable measurements.

## Blind Blackbox-Fuzzing Baseline (Work Plan item 3, Oct 2 2026)

Expected Outcome 2b claims "measurable increase in edge and branch coverage compared to baseline blackbox fuzzing." Until now every coverage number in this project was harness-vs-harness (informed vs. the Oct 1 "blind" ablation above) — there was no true control condition with no semantic harness at all. This section produces that baseline, run directly in this session (this sandbox has a working `clang++`/libFuzzer/ASan toolchain, confirmed before starting — no Antigravity round-trip was needed), with the same rigor and the same `llvm-cov` cross-validation applied to every other Stage 6 number.

### Scope note, stated explicitly before any result

A literal "no harness, no domain knowledge of which function even exists" baseline — the kind used in P2IM/Fuzzware-style research (a full firmware binary executed under QEMU with generic MMIO stubbing) — is a materially larger undertaking than this item was scoped for, and is **not** what's claimed here. That belongs to the already-tracked Fuzzware head-to-head (Work Plan item 7). What *is* feasible, and what was built: a per-function harness reduced to the practical minimum of engineering judgment this project's infrastructure supports, going one step further than the Oct 1 "blind" condition. The blind condition already removed per-field MMIO modeling (whole-struct `memcpy` instead of bitextracted fields) but still kept two things that encode real domain knowledge:

1. A minimum-input-size guard (`if (size < N) return 0;`) — this encodes "I know roughly how many bytes this function needs before it's worth exploring."
2. A semantic correctness assertion on the function's output — this encodes "I know what correct behavior looks like."

The new **blackbox** harnesses (`harnesses/blackbox/fuzz_pl011_{poll_in,poll_out,isr}_blackbox.cpp`) remove both: no size guard (short inputs are zero-padded, never rejected), and no correctness oracle beyond ASan/UBSan crash detection — exactly as a fuzzer with zero understanding of "correct" output would operate. One safety-driven exception is kept and flagged in the harness source itself: `pl011_isr`'s `irq_cb` is a function pointer, and raw-memcpying fuzzer bytes directly onto it would make the harness jump to an arbitrary address on most inputs — a harness memory-safety artifact, not a target-function finding. A single fixed, arbitrarily-positioned bit (byte 0, bit 0) chooses between `NULL` and one fixed dummy callback, the same mechanism the blind condition already used, not a reintroduction of per-field reasoning.

**A genuine, previously-undocumented build-reproducibility bug was found and fixed while compiling these**: the build flag `-Iharnesses/include` cited in `stage6_difficulty_metrics.md`'s "Tool Verification" section as the way to rebuild the original isolated harnesses actually fails on current `main` — not just for these new harnesses, for the pre-existing `fuzz_pl011_poll_in.cpp` too (confirmed by direct reproduction: `clang++ -Iharnesses/include harnesses/fuzz_pl011_poll_in.cpp` → `error: redefinition of 'device'`). Root cause: that flag resolves to the Ablation B v2 scaffolding's own non-empty `harnesses/include/zephyr/device.h`, which collides with these harnesses' own local `struct device` definition. Fixed by adding `harnesses/include_isolated/` (an empty `zephyr/device.h`, just enough to satisfy the real driver header's `#include <zephyr/device.h>` without redefining anything) and using that path instead. `stage6_difficulty_metrics.md`'s documented command should be corrected to use this path; flagged here rather than silently worked around.

### Methodology and results

Same protocol as the informed/blind conditions: 5 independent seeds × 15s wall-clock for `poll_in`/`isr`; 10 independent seeds, run-until-hang, `-timeout=3`, for `poll_out` (each seed given its own corpus directory — an initial run that shared one corpus directory across seeds was caught and discarded before being accepted, since later seeds would inherit earlier seeds' discovered inputs rather than running independently). `llvm-cov` cross-validated every result, same methodology as every other Stage 6 number (`-fsanitize=fuzzer -fprofile-instr-generate -fcoverage-mapping`, `llvm-profdata merge`, `llvm-cov report`). Raw logs in `blackbox_fuzz_logs/`, coverage reports in `blackbox_llvm_cov_logs/`, corpora in `blackbox_corpus/`, pinned binaries `fuzz_poll_in_blackbox`/`fuzz_poll_out_blackbox`/`fuzz_isr_blackbox`.

**Important caveat on comparing raw `cov:`/`ft:` numbers across conditions**: the blackbox harnesses are smaller/simpler C++ files than the informed/blind ones (fewer guard branches, no assertions), so each condition's binary has a *different total instrumented PC count* — raw sancov edge counts are not directly comparable across differently-sized binaries without normalizing. The `llvm-cov` source-level numbers below are the fair, apples-to-apples comparison; the raw sancov numbers are reported for completeness and internal consistency only.

| `poll_in` | Blind | `cov:11/ft:12` of 17 (identical to informed) | 96.55% / 95.35% / 91.67% |

### The headline finding: removing the size guard changes *when* the busy-wait is found, not whether coverage drops

Contrary to a naive expectation that "less domain knowledge → worse coverage," `poll_in` and `isr` show **no meaningful coverage loss** in the blackbox condition relative to informed/blind — consistent with the Oct 1 finding that these are shallow enough functions for libFuzzer's own coverage-guided search to rediscover the relevant bit patterns from scratch, with or without a semantic head start.

`poll_out` tells a sharper, genuinely new story. **All 10/10 blackbox seeds hit the busy-wait hang almost immediately** (at the very first post-`INITED` execution), versus the informed condition's modal 4/5 seeds (with only 1/5 fully immediate). This was investigated directly, not just reported: the exact hanging input was pulled from `blackbox_fuzz_logs/poll_out_seed1_timeout-...` and its bytes checked by hand against `struct pl011_regs`'s real layout (`fr` sits at byte offset 24–27). The hanging input is `0x0a` followed by 25× `0xff` — 26 bytes total, so bytes 24–25 (`0xff 0xff`) land exactly inside `fr`'s offset range, setting the TXFF bit (`BIT(5)`) and triggering the hang. **Mechanistic explanation**: the informed/blind conditions both reject any input shorter than `sizeof(regs)+1` (≈77 bytes) outright, so the fuzzer "wastes" a meaningful fraction of its budget on inputs that get silently discarded before ever reaching the function at all. The blackbox condition has no such guard, so even short, cheap-to-generate inputs are accepted and explored immediately — and because a single coverage-guided search converges on the hang-triggering pattern quickly regardless of overall input length, removing the guard lets the fuzzer reach it faster and more reliably, not less. This is a genuinely useful, non-obvious finding for the paper: a purely *structural* guard (minimum useful length) that carries no register-semantic knowledge still has real fuzzing-efficiency value, separate from and in addition to the per-field semantic modeling tested by the Oct 1 ablation.

## Work Plan Item 7: Fuzzware Head-to-Head Benchmark (Oct 3 2026)

* **Goal**: run Fuzzware's own toolchain (the field's reference MMIO-aware firmware re-host fuzzer for ARM Cortex-M/bare-metal targets) against AeroHarness's own case-study driver — a genuine head-to-head on the same code, not a shared-benchmark comparison against a different target or against published numbers from Fuzzware's own paper.

AeroHarness's own Stage 6 harnesses are host-compiled libFuzzer binaries. Fuzzware's bundled example targets (`examples/pw-recovery/`, `examples/P2IM/`) are pre-built closed-source blobs with no PL011/UART content (confirmed by `grep -rli "pl011\|uart"` across both directory trees — only generic board filenames matched). * **Target built**: `item7_fuzzware/` — a minimal bare-metal ARM Cortex-M4 firmware image, not a full Zephyr RTOS boot. It reuses the exact driver source and mock preamble already proven in `uart_pl011_wrapped.c` (same `struct pl011_data`/`pl011_config` field values as `fuzz_state_machine.c`'s dispatcher harness), with one change: `DEVICE_MMIO_GET` resolves to the real PL011 MMIO base address (`0x40000000`) instead of a process-local mock buffer, and `item7_fuzzware/config/config.yml` declares that address range as an `mmio_`-prefixed region. `item7_fuzzware/src/main.c`'s `app_main()` calls `pl011_init` once then loops `poll_out`/`poll_in`/`isr` forever — mirroring the dispatcher harness's own call sequence, but unconditionally rather than byte-stream-selected, since Fuzzware has no byte-stream to select from (see methodology note below). Minimal startup/vector-table/linker-script glue (`startup.c`, `link.ld`) built with the sandbox's existing `arm-none-eabi-gcc`; no Zephyr SDK, `west`, or board HAL needed.
  * **A latent width bug caught in the process, fixed before use, not after**: the mock preamble's `GENMASK`/`FIELD_PREP` macros hardcode a `63 - h` shift, which is only correct where `unsigned long` is 64 bits — true on the x86-64 host where the existing dispatcher harness runs, false on this 32-bit ARM target (`arm-none-eabi-gcc` gave `-Wshift-count-overflow` warnings on the very first build attempt). Fixed to `31 - h` in `item7_fuzzware/src/firmware_driver.c` before any fuzzing was run, since an uncaught UB-shift here would have miscomputed `PL011_IFLS_*` bitfield writes and made any result from this target meaningless. This is harness-infrastructure code, not the driver under test, so the fix doesn't change what's being fuzzed — it's the same class of catch as item 11's own docstring overclaim: verify the thing you just wrote before trusting results built on it.

* **A genuine methodological difference, not just a different tool** — documented rather than glossed over: AeroHarness's dispatcher harness (`fuzz_state_machine.c`) takes a fuzzer byte-stream and uses it to both select which API to call next *and* what value to inject into `dr`/`fr`/`mis`/`imsc`. Fuzzware has no such byte-stream — it fuzzes the **hardware's answers**, not firmware control flow: every MMIO load the firmware issues against the declared `mmio_pl011` region returns an AFL-mutated value, while the firmware's own code (which API to call, in what order) is fixed in `main.c`. Both approaches end up exercising the same driver functions with fuzzer-chosen register values; they just inject the fuzzing at a different layer (host byte-stream vs. emulated-hardware response), which is the actual, reportable point of comparison here — not an apples-to-apples "which tool found more bugs" framing alone.

### Diagnosis of the two triage-run anomalies (Oct 17 2026)

**`pl011_irq_tx_enable` (11/22 lines).** The uncovered lines are the `while (uart->imsc & PL011_IMSC_TXIM)` loop body (CTS handling and the `K_SPINLOCK` callback invocation). The cause is in the harness: it assigns `dev_data.irq_cb = nullptr` unconditionally, so the early return `if (!data->irq_cb) return;` is taken on every run in which `sw_call_txdrdy` is set (50.3k of 300k executions reached that return; none went further). The harness compiled, linked and passed the smoke test, so the pipeline recorded SUCCESS for a harness that cannot reach half of its target. Exercising the loop needs a non-null callback that clears the TX interrupt-mask bit, otherwise the loop does not terminate; a model avoiding that hazard is plausible but unconfirmed. Consequence: the compile + smoke oracles do not measure whether the target is exercised; a coverage signal would.

**`pl011_set_baudrate` crash input.** Decoded by hand using FuzzedDataProvider's from-the-end consumption order, the 102-byte reproducer yields `clk = 0x3f3f3f40` and `baudrate = 0x40000000` (2^30). The harness excludes only baudrate 0 (`ConsumeIntegralInRange(1, 0xFFFFFFFF)`), and `baudrate * 16U` is 0 in 32-bit arithmetic for 2^30, so the divisor is zero: the overflow variant, not the zero variant. The replay of the kept input reproduces `FPE ... pl011_set_baudrate.c:28:17`. Only 15 of 2^32 non-zero baudrate values (multiples of 2^28) produce a zero divisor, which is why a random campaign reaches it rarely and a 100,000-run gate can miss it.

**Proposed detector (not yet evaluated).** Clang's `-fsanitize=unsigned-integer-overflow` reports the wrap in `baudrate * 16U` for every baudrate >= 2^28 (15/16 of random values), i.e. on the first executions, independent of whether the divisor becomes zero. Unsigned wrap is defined behaviour and sometimes intended, so reports would be candidates, and precision across the 18 targets is unknown. `ubsan_wrap_probe.py` measures that (target-side reports per harness, fixed seed, no API calls); on a two-line fixture it flagged the wrap in under 2,000 runs.

### Coverage-feedback round added to the loop (Oct 17 2026, not yet evaluated)

Motivated by `pl011_irq_tx_enable` (SUCCESS at 50% driver-line coverage; its harness always nulled the interrupt callback). New optional step, `--coverage-feedback-min F` (default off): after a harness passes every oracle, line coverage of the target's own sources is measured with llvm-cov over a short campaign (20,000 executions, 30 s cap). If it is below `F`, the unreached lines (marked in the driver source) are sent to the model for exactly one round with instructions not to filter away faults in the code under test. The new harness replaces the verified one only if it compiles, passes the smoke test (and the stability gate and crash triage when enabled) and covers strictly more lines; otherwise the verified harness is kept. A crash in the driver that the round reaches is recorded as a candidate finding (stage `COVERAGE_FEEDBACK`). Offline tests cover accept, reject (not better, failed oracle, unchanged, measurement error) and the threshold; the coverage oracle was also run against real clang/llvm-cov on a small fixture. Combined with triage, the stability gate and the wrap probe, the next run is a labelled "full-loop" variant of the same 18 targets; its results are not available yet, and the original 18/18 protocol is unchanged.

## Work Plan Item 4: Third RTOS/Target Pipeline Run — Crazyflie Drone Firmware (Oct 20-25 2026)

* **Goal**: run Stage 6 (LLM harness synthesis + compiler-driven self-repair + libFuzzer/ASan fuzzing) end-to-end against `bitcraze/crazyflie-firmware`, a third RTOS/target pairing distinct from the Zephyr UART driver and the RIOT Kinetis ADC driver already covered — a different flight-controller codebase, built around a dual-MCU (STM32 + nRF51 radio coprocessor) `SyslinkPacket`/CRTP architecture rather than a single-MCU peripheral driver. Three target functions were run, pinned to commit `9912584c85db92dbbba14334ffed20ebabba463e`.

* **Target 1 — `radiolinkSyslinkDispatch` (`src/drivers/src/radiolink.c`), P2P-broadcast branch.** This target took five rounds of real harness-fidelity debugging before its result could be trusted, each caught by independently re-reading the pinned source rather than accepting the synthesis agent's own report:
  1. The synthesized stub silently dropped the `volatile` qualifier on `p2p_callback` (declared `static P2PCallback p2p_callback = NULL;` instead of the real `static volatile P2PCallback p2p_callback;`) despite the report claiming verbatim extraction. Fixed by restoring the qualifier and adding a `p2pRegisterCB` call as a second safeguard.
  2. The first fuzzing run on the fixed harness found a crash at `length=174` — impossible in the real system, since `uart_syslink.c`'s RX state machine discards any packet with `length > SYSLINK_MTU` (64) before it ever reaches dispatch. Fixed by adding that missing precondition guard to the harness.
  3. The next report "validated" the P2P-broadcast finding by hand-constructing a `length=63` input using foreknowledge of the already-suspected signature, rather than letting the fuzzer discover it — a hand-fed result, not an autonomous one, and logged as such rather than accepted.
  4. libFuzzer's single-process mode exits on the very first sanitizer violation, so a second, larger-radius defect in the same branch was found but the original one-byte overflow was never explored further. Fixed by switching to fork mode with `-ignore_crashes=1` from that point on.
  5. A run on nominally-empty seed corpus returned 2,638 structurally identical "crashes" from a single, deterministic libFuzzer bootstrap input (`Unit U({'\n'})`, `FuzzerLoop.cpp:809-811`, independently confirmed by reading that exact LLVM source) rather than genuine exploration — initially mis-suspected as corpus poisoning (retracted once an `ls -la` check and the libFuzzer source itself confirmed the real cause), fixed by seeding the corpus with 5 valid, non-crashing packets before any fuzzing run.
  * **Result, found via genuine coverage-guided fuzzing on the corrected harness, not hand-fed**: a 1-byte stack-buffer overflow in the `SYSLINK_RADIO_P2P_BROADCAST` branch at `length=63` (`p2pDataLength=61`, one byte past `P2PPacket.data[60]`, where `P2P_MAX_DATA_SIZE=60`). Radio-reachable: nothing upstream of this dispatch point validates `p2pDataLength` against the packet's actual payload capacity.
  * A second, larger stack-buffer overflow was also found in the same branch at `length<2` (`p2pDataLength` underflowing to ~254) — real at the harness level, but independently confirmed **not** radio-reachable: the nRF51 coprocessor's own `main.c` requires `packet->size>=2` before it will even tag a packet as P2P, so this path cannot be triggered from the radio link in the real two-MCU system. Reported as a harness-only finding, not a system-level vulnerability.

* **Target 2 — `crtpCommanderHighLevelWriteTrajectory` (`src/modules/src/crtp_commander_high_level.c:1047-1053`).** Chosen for structural variety (fixed-size buffer + two numeric parameters, rather than a packet-type switch). The five lessons from Target 1 (verbatim extraction including qualifiers, matching the real caller's actual parameter range rather than the callee's widest declared type, seeding the corpus before fuzzing, fork mode with `-ignore_crashes=1` from the start, periodic status sampling across the run) were written into the synthesis prompt up front; the harness synthesized and found its result on the first attempt, with no further fidelity debugging needed.
  * **Result**: a CWE-190 integer-overflow-bypasses-bounds-check defect. The real bounds check is `if ((offset + length) <= sizeof(trajectories_memory))` — when `offset` is numerically close to `2^32`, the unsigned addition wraps, so a small `length` can satisfy the check even though `offset` itself is far outside the 4096-byte `trajectories_memory` array, and the subsequent `memcpy` writes out of bounds. Reachable end-to-end: `offset` is copied as a raw, unvalidated 4-byte field directly from an incoming CRTP memory-write packet (`crtp_mem.c`, `memWriteProcess`) with no upstream range check before it reaches this function.
  * **Caveat flagged for the paper's limitations section, not yet hardware-confirmed**: the test harness runs on a 64-bit host, where the resulting out-of-bounds write is effectively unbounded (wild pointer arithmetic can address far outside any mapped region). On the real 32-bit STM32F405 target, the same wraparound is bounded by 32-bit pointer arithmetic, making the actual out-of-bounds write more constrained/controllable than what the 64-bit sandbox demonstrates. This severity nuance was derived independently during review, not reported by the synthesis pipeline itself.

* **Target 3 — `logAppendBlockV2` (`src/modules/src/log.c:398-464`).** Chosen for a third structural shape again (a small fixed lookup table indexed by an incompletely-masked field, rather than a byte-array copy or an arithmetic bounds check). Also synthesized and found its result on the first attempt.
  * **Result**: a global-buffer-overflow read (CWE-125). `logAppendBlockV2` indexes `typeLength[settings[i].logType & LOG_TYPE_MASK]`, where `LOG_TYPE_MASK` is `0x0f` (permitting index values 0-15) but `typeLength[]` only has defined entries for the enum values 1-8 (array size 9) — the mask and the table's real valid range don't agree. Reachable via the routine CRTP log-block-configuration command (`logControlProcess`), which copies the 1-byte `logType` field directly from an incoming packet with no range check before this call. A secondary, related bounds-check bug was also noted in the same file's `appendToPacket` (`log.c:548`, `if (pk->size <= CRTP_MAX_DATA_SIZE - n)`), not independently fuzzed as its own target.
  * **Minor correction caught on review**: the synthesis agent's own report table had an internal arithmetic inconsistency in how it labeled out-of-bounds offsets for several of the triggering index values, contradicted by its own cited ASan trace. Independently re-derived (offset = index − 9 for indices 9-15) and confirmed against the ASan trace, which reports an access "2 bytes after" a size-9 array for index 11 — consistent with the corrected arithmetic. Does not affect whether the underlying finding is real; logged as a documentation-accuracy fix only.

* **A practical pipeline limitation surfaced and worked around, not hidden**: the LLM harness-synthesis tool used for this run (Antigravity) runs on its own underlying model (Gemini), separate from the OpenRouter/DeepSeek model the synthesis pipeline itself calls. That Gemini layer repeatedly content-filtered prompts that explained a target's security-relevant mechanism in advance — even when framed neutrally or academically (two rewrite attempts, both still blocked). The filter only reliably passed once all mechanism explanation was removed from the prompt, leaving purely procedural instructions (read this function, extract it verbatim, build a harness, seed and fuzz it, report what's found) — which also happens to be consistent with this project's own standing "don't hand-feed the fuzzer the answer" principle (the same discipline that flagged the hand-fed Target 1 validation above as not autonomous).
